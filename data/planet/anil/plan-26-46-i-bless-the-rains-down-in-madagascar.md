<h3><a href="https://anil.recoil.org/news.xml#a-local-perma-caching-zarr-proxy" class="anchor" aria-hidden="true"></a>A local perma-caching Zarr proxy</h3>
<p>We serve <a href="https://anil.recoil.org/projects/tessera">Tessera</a> embeddings as <a href="https://anil.recoil.org/notes/tessera-zarr-v3-layout">Zarr v3 shards over HTTP</a>, which works very well until offline access is needed or we're re-reading the same shards for the hundredth time (something that's causing significant stress on our Cambridge outbound bandwidth lately!). The <a href="https://anil.recoil.org/papers/netapp-tr-3071">classic way</a> to solve this is by using an HTTP caching proxy which can intercept requests before they go to the network.</p>
<p>Therefore I built <code>zarr-perma-proxy</code> in my <a href="https://tangled.org/anil.recoil.org/ox">ox monorepo</a>, which acts as a specialised 'permanent' disk cache for immutable public HTTP objects. The proxy understands the pattern of Zarr v3 HTTP requests, so a cache miss downloads the complete shard with a single upstream request. After that, every byte range request (for an individual chunk) is served from local disk.</p>
<p>The upstream shard files sitting on the remote server aren't decoded or processed, and since those stores are immutable there's no cache revalidation necessary. I've still got to make the on-disk cache format compatible with <a href="https://github.com/ucam-eo/geotessera">geotessera</a> so it can directly read the files, but this works pretty well for now.
I also opened a <a href="https://github.com/ucam-eo/geotessera/pull/461">PR to geotessera</a> that adds <code>--proxy</code>, <code>GEOTESSERA_PROXY</code> and a <code>proxy=</code> argument, so that existing Python readers can route their Zarr reads through the permaproxy.</p>
<p>This has two main uses for me so far:</p>
<ul>
<li>On my laptop, it keeps a permanent local copy of whatever portion of the Tessera embeddings I'm using, for demos and offline analysis.</li>
<li>On our big petabyte storage in Cambridge, it keeps a copy of whatever embeddings people in the group are pulling. Everyone in our group working on habitat mapping, like <a href="https://aneeshnaik.github.io/">Aneesh Naik</a>, <a href="https://mynameismwd.org">Michael Dales</a> and <a href="https://patball1.github.io">James G. C. Ball</a>, will need to do a global run of their <a href="https://anil.recoil.org/ideas/tessera-habitat-maps">habitat models</a> as they <a href="https://digitalflapjack.com/weeknotes/2026-11-16/">approach</a> <a href="https://www.aneeshnaik.com/blogposts/20261111_weeknotes_2026_45.html">maturity</a> on smaller regions.</li>
</ul>

<h3><a href="https://anil.recoil.org/news.xml#a-hydrology-model-for-next-years-drought" class="anchor" aria-hidden="true"></a>A hydrology model for next year's drought</h3>
<p>The WMO <a href="https://wmo.int/news/media-centre/el-nino-set-become-very-strong-raising-risks-of-extreme-weather-2027">reported</a> in September that El Niño is firmly established and set to become a very strong event, raising the risks of extreme weather into 2027. So I've been working with <a href="https://toao.com">Sadiq Jaffer</a>, <a href="https://www.linkedin.com/in/pedro-marques-sousa">Pedro Sousa</a>, <a href="https://rich-turner-group.github.io/">Rich Turner</a> and <a href="https://github.com/ctk21">Tom Kelly</a> on a data-driven hydrology model of the UK, to help figure out if we can do an improved forecast for the UK's drought situation next year.</p>
<p>There's plenty of excellent prior art in this space, of course, and our hope is that Tessera will be particularly useful for <a href="https://anil.recoil.org/papers/2026-weather-downscaling">downscaling</a>. Tom has been writing up notes on his blog that are an excellent primer if (like me) you are new to the field:</p>
<ul>
<li><a href="https://ctk21.github.io/2026/11/12/intro-to-gr4j/">What are the GR4J and GR6J hydrology models</a> covers the classic "lumped conceptual" approach, which represents an entire river catchment as a small number of interconnected reservoirs to avoid having to simulate them individually.</li>
<li><a href="https://ctk21.github.io/2026/11/13/intro-to-net-rainfall-runoff/">Intro to net based rainfall-runoff models</a> surveys the neural approach, from an LSTM trained <a href="https://doi.org/10.5194/hess-23-5089-2019">across US catchments</a> through to the global model behind Google's <a href="https://sites.research.google/floods/">Flood Hub</a>.</li>
<li><a href="https://ctk21.github.io/2026/11/16/data-for-rainfall-runoff/">What data do rainfall–runoff models need?</a> catalogues the inputs needed, from streamflow observations and catchment attributes to historical meteorology and forecasts.</li>
</ul>
<p>Also on my reading list is Google DeepMind <a href="https://deepmind.google/blog/opening-the-datasets-behind-our-ai-weather-models/">opening the datasets behind their AI weather models</a>. These include SatWeave, a global mosaic of geostationary satellite imagery, and <a href="https://arxiv.org/abs/2611.13941">PARDIG</a>, which gives global precipitation estimates at 0.1° and 15-minute resolution learnt from sparse spaceborne radar measurements.</p>
<p>This also puts the Environment Agency hydrology data I gathered for the <a href="https://anil.recoil.org/notes/2026w44">UK label map</a> to good use. My agentic crawling of the UK data continues (politely, respecting rate limits) apace, with over 250 separate data sources now included! I'm going to sift through them in more detail next week to figure out which would be useful towards the hydrology model.</p>

<h3><a href="https://anil.recoil.org/news.xml#counting-birds-with-citizen-science-data" class="anchor" aria-hidden="true"></a>Counting birds with citizen science data</h3>
<p>We had a brilliant <a href="https://www.conservation.cam.ac.uk">CRI</a> <a href="https://www.conservation.cam.ac.uk/events/cri-seminar-tracking-nature-citizen-science-data">seminar</a> from <a href="https://www.st-andrews.ac.uk/mathematics-statistics/people/ap48">Prof Ali Johnston</a> of St Andrews on "<a href="https://www.conservation.cam.ac.uk/events/cri-seminar-tracking-nature-citizen-science-data">Counting birds with citizen science data</a>", all about <a href="https://ebird.org">eBird</a> and the huge efforts to turn tens of millions of birdwatchers' checklists into actionable insights for conservation practitioners.</p>
<p><img src="https://anil.recoil.org/images/26w46-1.webp" alt="%c" title="Ali Johnston kicking off her seminar on counting birds with citizen science data"></p>
<p>The talk focused on the statistical corrections needed to make sense of the 'raw' crowd data. While birds are the most <a href="https://dashforlife.org">surveilled taxa</a>, the tracking records vary in quality from rigorously designed surveys like the BTO's <a href="https://www.bto.org/get-involved/volunteer/projects/bbs">Breeding Bird Survey</a> through to a casual list that's scribbled in a notebook while on a walk (these are my sort of records!).</p>
<p>The eBird database from Cornell is somewhere in between these, as its <a href="https://ebird.org/about/tracking-your-lists-with-ebird">digital checklists</a> record enough about the effort that the individual involved puts in (e.g. how long, how far, whether everything seen was reported) to allow much of the bias to be modelled out afterwards. This is where Ali, the statistics expert, comes in!</p>
<p><img src="https://anil.recoil.org/images/26w46-2.webp" alt="%c" title="The spectrum from rigorous survey design to casual birdwatching, with eBird checklists in between"></p>
<p>Once those bias corrections are in place, the results she showed are remarkable. The example above shows weekly relative abundance maps for the Barn Swallow across its entire global range. This is much more detailed in both space and time than a conventional <a href="https://anil.recoil.org/projects/life">AoH</a> map is. The guidelines for doing this properly are in <a href="https://doi.org/10.1111/ddi.13271">Johnston et al</a> (2021).</p>
<p><img src="https://anil.recoil.org/images/26w46-3.webp" alt="%c" title="Weekly relative abundance of the Barn Swallow from eBird, versus the conventional range map inset"></p>
<p>This is of course directly relevant to our <a href="https://anil.recoil.org/ideas/tessera-habitat-maps">habitat mapping</a> efforts with Tessera. <a href="https://mynameismwd.org">Michael Dales</a> timed his Cambridge visit to coincide with the seminar and has <a href="https://digitalflapjack.com/weeknotes/2026-11-16/">written up</a> his conversations with Ali and her students. It's particularly intriguing to see that 'complete' eBird checklists are a good source of absence data, which is the missing thing in most occurrence datasets.</p>
<h3><a href="https://anil.recoil.org/news.xml#samosas-themis-and-a-haven-for-nature" class="anchor" aria-hidden="true"></a>Samosas, Themis and a Haven for nature</h3>
<p>This week's <a href="https://anil.recoil.org/notes/2026w42">samosa social</a> at Pembroke had a treat for the early comers, as they got a five minute talk from <a href="https://mlg.eng.cam.ac.uk/carl/">Carl Edward Rasmussen</a> about his <a href="https://mlg.eng.cam.ac.uk/carl/climate/themis0.pdf">Themis Mechanism</a> for equitable global emission reduction.</p>
<p><a href="https://www.conservation.cam.ac.uk/directory/dr-tom-swinfield">Thomas Swinfield</a> also brought up the parallels of Themis with his work on forest conservation in <a href="https://canopypact.uk">Canopy PACT</a>, the charitable spinout from <a href="https://anil.recoil.org/projects/4c">4C</a>.
Canopy PACT hit a big milestone this week, as the <a href="https://www.haven-climate.com">Haven</a> scientific protocol that we've been working on with <a href="https://isometric.com">Isometric</a> has soft-launched. Haven exists to protect forests by bringing scientific rigour, buyer demand and ecosystem alignment to nature-based reductions credits, at a time when confidence in those credits (and so the financing for forest conservation) has <a href="https://anil.recoil.org/notes/redd-overcrediting">fallen</a>. I'll write more about Haven once it's fully launched, but just look at the Madagascar video above for why I care so much about ensuring equitable livelihood benefits!</p>

<h3><a href="https://anil.recoil.org/news.xml#discussing-the-future-of-the-cst-tripos" class="anchor" aria-hidden="true"></a>Discussing the future of the CST Tripos</h3>
<p>We had our Computer Science departmental annual report this week, in which we considered the future of Part II and Part III. One concern is that increasing the number of Part III students would roughly double the effort needed for undergraduate project supervision.</p>
<p>Some suggestions included letting students elect at the start of Part II whether to graduate after three or four years (with one dissertation in their final year), or instead following Engineering with smaller one-term Part II projects, or dropping the Part II project altogether (something I'm very much against as the experience of building something end-to-end is super valuable).</p>
<p>We're seeing a fall in our applications as many <a href="https://www.bcs.org/articles-opinion-and-research/computings-pipeline-problem-is-more-nuanced-than-headlines-suggest/">other departments are</a> internationally. I suspect we're going to move to a longer four-year programme that caters to those who really want to learn computer science, and that this will justify the extra supervision efforts required.</p>

<h2><a href="https://anil.recoil.org/news.xml#making-ocaml-and-oxcaml-more-deployable" class="anchor" aria-hidden="true"></a>Making OCaml and OxCaml more deployable</h2>
<p>As we're using <a href="https://anil.recoil.org/projects/oxcaml">OxCaml</a> more and more for our services, I need a way to quickly deploy binaries to various machines without having to set up a compiler toolchain on each of them.</p>
<h3><a href="https://anil.recoil.org/news.xml#self-hosted-atproto-pipelines-on-tangled" class="anchor" aria-hidden="true"></a>Self-hosted ATProto pipelines on Tangled</h3>
<p>To that end, I've spent a lot of time this week extending <a href="https://anil.recoil.org/notes/2026w45">last week's custom spindle</a> into an end-to-end, completely self-contained ATProto infrastructure that lives in my <a href="https://tangled.org/anil.recoil.org/ox">monorepo</a>. The idea is to use the <a href="https://tangled.org">Tangled</a> lexicons to drive our own self-hosted runners, and so be ready for when private repository support lands on Tangled.</p>
<p>This is all a work in progress, but the rough shape is:</p>
<ul>
<li>OxCaml libraries for the ATProto plumbing, and a spindle that listens for pushes and pull requests and hands the builds off to our <a href="https://github.com/ocurrent/ocluster">OCluster</a> pool, so nothing from a repository runs on the spindle host itself.</li>
<li>Automated odoc generation for every package in the monorepo.</li>
<li>Publishing of signed OS packages (deb, rpm and apk) with their repository indexes, to make it easier to deploy binaries of our services without needing an OxCaml toolchain on the target machine.</li>
<li>Disposable macOS VMs as a CI target alongside the Linux and Windows workers.</li>
</ul>
<p>You can watch me testing things on the <a href="https://tangled.org/anil.recoil.org/ox/pipelines">pipelines page</a>. I'll blog properly once it's live.</p>

<h3><a href="https://anil.recoil.org/news.xml#towards-a-merge-queue-deployment-prototype" class="anchor" aria-hidden="true"></a>Towards a merge queue deployment prototype</h3>
<p>This also links back to my thoughts from 2023 on moving the opam repository to <a href="https://github.com/avsm/opam-repo-roadmap-thoughts">merge queues</a>. <a href="https://github.com/raphael-proust">Raphaël Proust</a> and some of the other opam-repository maintainers have expressed interest in seeing a demo of how this could work. <a href="https://www.tunbury.org/">Mark Elvers</a> built a prototype of this for me earlier in the year using day10 on a self-hosted runner with GitHub's built-in merge queue to <a href="https://www.tunbury.org/2026/04/02/opam-overlay-ci/">gate PRs to an opam overlay repository</a>, so now I'm trialling it on ATProto.</p>
<p>I was also reminded of how useful this would be while merging many PRs into the opam-repository this week. These were mostly new releases (including Forester 6.0) but also a very long run of bounds fixes from <a href="https://github.com/samoht">Thomas Gazagnaire</a> as he prepares <a href="https://gazagnaire.org/blog/2026-11-09-alcotest-dune-release.html">Alcotest 1.10</a>. We <em>have</em> to make the human labour in verifying such changes much easier, which I believe merge queues are a step towards.
Mark has since gotten his <a href="https://www.tunbury.org/2026/11/16/week-46/">day10 builder working on Windows and the BSDs</a>, running in parallel with the existing opam-repo-ci jobs. This should also make merge queues much faster to use, I hope!</p>
